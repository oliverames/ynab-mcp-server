# Explained category suggestions

`suggest_transaction_categories` is read-only. It produces a recommendation and evidence for each selected uncategorized expense, or an explicit reason to abstain. It never calls a financial write API, updates a payee rule, or uses a paid model.

The default targets are uncategorized transactions, newest first, up to 50. `transactionIds` selects exact rows; `sinceDate` filters default targets only. `limit` (1–100) caps targets, never historical evidence. `asOfDate` defaults to the current UTC date. The handler requests all transaction history from `1970-01-01`, without a delta cursor, plus current categories and schedules. Returned freshness timestamps, server knowledge, and requested history coverage describe the read. Historical evidence is kept even when target selection covers a recent window.

Identity comes from the exact payee ID in the same budget. Merchant display names, imported bank names, and memos do not establish identity and are never parsed as instructions. Two payees with the same name do not share evidence. Recommendations use active visible categories and approved, nontransfer, nonsplit expenses. Duplicate IDs cannot add votes, deleted rows cannot vote, and hidden/deleted/internal categories are excluded.

History weights halve every 90 days. A history recommendation requires at least three reviewed expenses supporting the leading category, at least one within 180 days, and at least 85% of recency-weighted evidence supporting that category. Five supporting expenses, three recent, and at least 95% support earn a `high` label; other qualifying recommendations are `medium`. These are transparent heuristic support labels, not calibrated probabilities. Evidence includes category alternatives, reviewed and recent counts, sample transaction IDs, and the recency rule.

A schedule can provide a `medium` recommendation when its exact payee and account match, the next occurrence is within seven days of the transaction, and the expense amount is within the greater of 500 milliunits (0.50 budget currency units) or 1%. A matching schedule strengthens consistent history. Conflicting schedules or disagreement between a matching schedule and leading history cause abstention. Schedule evidence is deliberately limited to upcoming occurrences; the tool does not invent past schedule dates.

Mixed category merchants, recent reviewed split history, matching split schedules, missing IDs, insufficient or entirely old history, transfers, target splits, refunds/income, invalid/future dates, missing/deleted rows, and already categorized targets receive no proposed edit. Split parts require individual review rather than a parent-category guess. This conservative tool recommends expense categories; refund and income review remain separate workflows.

`proposed_edits` contains only `{ id, categoryId }` entries suitable for a later `update_transactions` request. It contains neither `confirmed:true` nor a write-preview token. Present the specific proposals and their evidence, create an exact session-bound preview through the write gate, and obtain explicit user approval before execution. A recommendation, confidence label, or preview token is not consent. The write gate must reread and validate current state; the suggestion's timestamps do not authorize a write.

This module adds deterministic recommendations and explicit abstention to the existing category search and unapproved transaction review. Existing `search_categories` still finds categories by names, and `get_transactions` still exposes payee history for manual review. No parser or automatic import/categorization scope is added. The implementation is original; no upstream code is copied.

Run the synthetic offline regression suite with `node --test test/category-suggestions.test.mjs`. It covers localization, payee identity, recency, uncertain merchants, schedules, splits, tombstones, transfers/refunds, malicious bank text, complete-history selection, write abstention, and separate budgets.
